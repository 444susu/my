# 二、进入模块 B 前必须补的两个关键检查

## B1. 必须检查同一 `(crop_id, season)` 在不同地块类型上的销售价格是否一致

当前模型指南中销售变量 `q(j,t,k)`、`e(j,t,k)` 是按“作物—年—季”汇总的。

因此，如果同一个 `(j,k)` 在不同地块类型上的 `price_mid` 不一致，则不能直接使用单一 `price[j,k]` 乘汇总 q/e，否则收入计算会失真。

模块 A 必须新增审计：

```text
对 parameters 按 (crop_id, season) 分组，统计 price_mid.nunique()
```

### 通过标准

若所有可能跨地块类型出现的 `(crop_id, season)` 都满足：

```text
price_mid.nunique() == 1
```

则可以安全降维为：

```python
price[(j, k)]
```

### 若不通过

必须停止进入模块 B，并报告哪些 `(crop_id, season)` 存在多价格。

此时需要重新决定销售变量/收入建模方式，例如保留来源地块类型维度，而不能 Codex 自行取均值。

这属于**硬门控检查**。

---

## B2. 必须检查“2023 最后实际季次”与地块类型规则的一致性

当前 adjacency 只检查 `last_season_2023` 非空且属于三个合法字符串，但还应进一步检查它是否符合对应地块类型的实际种植制度。

推荐规则：

- 平旱地/梯田/山坡地：最后季次必须为 `单季`；
- 普通大棚/智慧大棚：若 2023 数据完整使用两季，则最后季次应为 `第二季`；
- 水浇地：允许 `单季` 或 `第二季`，不应以 `第一季` 作为全年最后实际季次（若出现则说明 2023 数据或 season 处理异常）。

模块 A 应新增 `adjacency_consistency` 门控，并输出异常地块明细。

这项检查的目的不是新增农业假设，而是确保当前 `season_rank` 与历史数据确实产生了正确的“最后种植季”。
